# Tools Pagination

MetaMCP implements server-side pagination for `list_tools()` responses, enabling efficient handling of large tool sets (1000+ tools).

## Why Pagination?

Without pagination, fetching 2,000+ tools takes **43+ seconds** due to JSON serialization and parsing overhead. With pagination:
- **First page**: ~1-2 seconds (50 tools)
- **Agent early exit**: If tools are found in first page, no further fetches needed
- **Full fetch**: ~5-10 seconds across all pages

## How It Works

1. Client calls `list_tools()` with optional `cursor` parameter
2. Server returns a page of tools (default: 50) with `nextCursor`
3. Client fetches next page using `nextCursor` until `nextCursor` is null

```
Request: { method: "tools/list", params: {} }
Response: { tools: [...50 tools...], nextCursor: "50" }

Request: { method: "tools/list", params: { cursor: "50" } }
Response: { tools: [...50 tools...], nextCursor: "100" }

Request: { method: "tools/list", params: { cursor: "100" } }
Response: { tools: [...remaining tools...], nextCursor: null }
```

## Configuration

Set page size via environment variable:

```bash
# Default: 50 tools per page
MCP_TOOLS_PAGE_SIZE=50

# Larger pages (fewer requests, larger responses)
MCP_TOOLS_PAGE_SIZE=100

# Smaller pages (faster first response)
MCP_TOOLS_PAGE_SIZE=25
```

## Namespace-Level Caching

Tools are cached at the **namespace level** for maximum performance:

### How It Works

1. **Pre-warming**: When an idle MetaMCP server is created, tools are fetched in the background
2. **Cache sharing**: All sessions in a namespace share the same cached tool list
3. **Fast responses**: Subsequent `list_tools()` calls return cached data in ~50ms

### Cache Lifecycle

- **Pre-warmed on startup**: Cache is populated when idle servers are created
- **Invalidated on config change**: Cache is refreshed when MCP servers are added/updated/removed
- **TTL-based expiration**: Cache expires after 1 hour (configurable)
- **Shared across sessions**: Multiple agent connections reuse the same cache

### Configuration

```bash
# Cache TTL in seconds (default: 3600 = 1 hour)
# Set to 0 to disable TTL (never expires until invalidated)
MCP_TOOLS_CACHE_TTL=3600
```

### Performance Impact

| Scenario | Without Namespace Cache | With Namespace Cache |
|----------|------------------------|---------------------|
| First page (cold) | 38-39s | 38-39s |
| First page (warm) | 38-39s | **~50ms** |
| All pages (warm) | 38-39s | **~3s** |

The key improvement: With namespace-level caching, new agent sessions get instant cache hits instead of fetching from upstream servers.

## Cache Staleness & Risk Mitigation

### When Does Cache Become Stale?

The namespace cache may not reflect the latest tools from upstream MCP servers in these scenarios:

| Scenario | Example | Cache Behavior |
|----------|---------|----------------|
| **Upstream server adds tools** | Arcade adds 100 new tools | Cache won't reflect until TTL expires or invalidated |
| **Tool schema changes** | Tool parameters updated | Same as above |
| **Server restart** | MetaMCP container restarts | Cache is cleared, re-warmed on first request |

### Automatic Cache Refresh

Cache is automatically refreshed when:

1. **Background refresh** (NEW) - Proactively refreshes at 80% of TTL (48 min for 1-hour TTL)
2. **TTL expires** (default: 1 hour) - Fallback if background refresh fails
3. **Config change** - Adding/editing/removing MCP servers invalidates cache
4. **Server restart** - Fresh cache is pre-warmed

### Background Refresh (Always-Warm Cache)

MetaMCP runs a background job every 5 minutes to check cache entries:

- **Proactive refresh**: Entries are refreshed when they reach 80% of their TTL
- **No client wait**: Refresh happens in background, clients always get instant responses
- **Failure tolerant**: If background refresh fails, stale data is served until next attempt

Example timeline (1-hour TTL):
```
0:00  - Cache warmed (2852 tools)
0:48  - Background refresh triggers (80% of TTL)
0:48  - New tools fetched, cache updated
1:36  - Next background refresh
...   - Cache never expires, always warm
```

### Manual Cache Refresh Options

For immediate refresh without waiting for TTL:

1. **Force Refresh** - Pass `forceRefresh: true` in `list_tools()` request
2. **Edit MCP server config** - Any change (even reverting) triggers invalidation
3. **Restart MetaMCP** - Clears all caches and pre-warms fresh data
4. **Shorter TTL** - Set `MCP_TOOLS_CACHE_TTL=300` for 5-minute refresh

### Force Refresh API

Request fresh tools from upstream, bypassing cache:

```
Request: { method: "tools/list", params: { forceRefresh: true } }
```

- Invalidates namespace cache before fetching
- Fetches fresh data from all upstream MCP servers
- Re-warms cache with new data
- Used by "Refresh Tools" button in MetaMCP UI

### Recommendations

| Use Case | Recommended TTL | Rationale |
|----------|----------------|-----------|
| **Production** | 3600 (1 hour) | Good balance of performance and freshness |
| **Development** | 300 (5 min) | Faster feedback on upstream changes |
| **Stable tools** | 0 (no TTL) | Never expires until manually invalidated |
| **Volatile tools** | 60 (1 min) | Near real-time sync, higher load |

### Monitoring

Check cache status via logs:

```
[ToolCache] Cache HIT: 2852 tools for 2c714f73... (age=5159ms)
[ToolCache] Cache already warm for 2c714f73..., skipping warm
[ToolCache] Cache MISS: warming cache for namespace 2c714f73...
```

## Client Compatibility

**Backward compatible**: Clients that don't use pagination receive the first page (50 tools).

**Pagination-aware clients** (like OAP LangGraph agent) can:
- Fetch pages incrementally
- Exit early once requested tools are found
- Reduce initialization time from 43s to &lt;2s
